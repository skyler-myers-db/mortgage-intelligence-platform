Since post-w5/deploy-hardening (2026-10-27) `tools/databricks/provision_runtime_secrets.py` plans every write first. An existing `cotality-id-mask-v1` must equal the configured `MIP_COTALITY_ID_MASK_SECRET` as the runtime reads it (UTF-8, stripped), compared as HMAC-SHA256 under a per-run random salt; differ, unreadable, or an empty `value` answer (`EmptySecretValue`) -> `RuntimeSecretChangeRefused`, exit 2, nothing written. An existing `genie-action-current` is compared the same way but only NOTED (unchanged / rotated with grace / changed with no grace key / not compared), never refused: it is NOT an enforced gate, the owner reads it. Unset `SALESFORCE_*` keeps an existing key; the payload never binds a kept key. Both sides read a placeholder secret input (`<x>`, `changeme`) as unset through `runtime_secret_text` (round 2 closed the edge; `tests/unit/test_salesforce_secret_binding_parity.py`). `--check` is read-only and runs at the end of the step-0 preflight, before step 0a stops the App. Every CLI mode first proves the SDK-resolved host equals every configured install host (`DATABRICKS_HOST` shell/.env.local, `MIP_DATABRICKS_WORKSPACE_HOST`), refuses with none configured, and prints the host on its summary line.

**Why:** a changed mask re-keys every `B-…` id and orphans the ids stored in Lakebase; the old tool overwrote mip-runtime unconditionally, and the write runs after the App stop. The secrets/get read works only for a workspace admin: `databricks secrets get-secret --help` (CLI v1.10.0) says a normal user gets BAD_REQUEST outside a notebook. The first-round proof here (a nonexistent-key probe returning RESOURCE_DOES_NOT_EXIST) was WRONG as proof: the existence check answers before any caller check. The governance verifier re-proved it on an EXISTING key as an admin (paychex, read-only, booleans only); each read leaves a getSecret audit entry. deploy.sh already requires a workspace-admin deployer, so the guard is viable. Round 2 (verifier L3-G1, L3-G2) found two holes the first round shipped: the keep-on-unset rule used a different notion of "unset" than the payload's binder (a placeholder kept the stored credential AND bound it), and run by hand the tool's `WorkspaceClient()` fell back to the DEFAULT profile (pr105 on the owner's machine) without saying which workspace it read.

**How to apply:** never add a "rotate the mask" flag to the provisioner; a re-key is an owner data migration. Any new secret that keys persisted data gets the same fingerprint guard and a pre-stop `--check`. A keep-on-unset rule must share its "unset" predicate with whatever binds the key, and gets a parity test over {empty, placeholder, real}. A by-hand tool that reads secrets must prove and print the workspace host it resolved before its first call. Prove a read-path permission on an EXISTING object, never on a missing one. Tests must record the fingerprints (`_record_fingerprints`) and assert none leaks, with HIGH-ENTROPY fixtures and an 8-character window check: a bare "value not in message" check let a `.hex()` fingerprint through, and `value[:12]` over `label-xxxx` fixtures let a `configured[-16:]` leak survive.
