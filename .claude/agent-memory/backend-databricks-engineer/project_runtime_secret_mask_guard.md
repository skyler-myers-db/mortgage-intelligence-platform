Since M0-PR2 (2026-10-29, superseding the 2026-10-27 salted-fingerprint mask guard) `tools/databricks/provision_runtime_secrets.py` is presence-only. The plan lists the scope's keys and never calls `get_secret`: an existing `cotality-id-mask-v1`, `genie-action-current` or `genie-action-previous` is kept whatever the inputs say (a set input is named in a "kept unread" note), and an unset `SALESFORCE_*` keeps its key. An absent mask or current key is written once from its optional shell/.env.local input or `secrets.token_hex(32)`; an absent previous or salesforce key gets the `disabled.` sentinel. Each write is read back for presence (listed), never for its value. A configured `SALESFORCE_*` input still replaces its key (third-party credential; the payload binds it only when set, `tests/unit/test_salesforce_secret_binding_parity.py`). `--require-existing` exits 2 on any planned write, scope creation included. `--rotate-genie-action` (human-run, refuses when `GITHUB_ACTIONS` is set) reads current, writes it to previous FIRST, then a new current. The three inputs are gone from every workflow and from deploy.sh's preflight (`tests/unit/test_runtime_secret_inputs_stay_out_of_ci.py`). Every CLI mode first proves the SDK-resolved host equals every configured install host and prints it.

**Why:** a changed mask re-keys every `B-…` id and orphans the ids stored in Lakebase; the fingerprint guard needed the stored value on the runner and the value in CI, and every run still rewrote `genie-action-current` and re-disabled `genie-action-previous`. Presence-only removes all three. A scope that lists `genie-action-current` or a `salesforce-*` key WITHOUT the mask refuses (`MaskKeyMissingRefused`, exit 2, pre-stop): the mask is written first, so that is a deleted mask, and only `MIP_COTALITY_ID_MASK_SECRET` restores it (`genie-action-previous` alone does not count: `--retire-previous` may create it first). The open hazard: a scope listing NO runtime key (a misnamed `MIP_RUNTIME_SECRET_SCOPE`, or one recreated empty) still looks like a first install and mints a NEW mask, so adopting an existing install should run `--check --require-existing`. A governed rotation has no grace window: the payload binds previous only when a `MIP_GENIE_ACTION_SECRET_PREVIOUS` value is configured (`test_payload_omits_stale_previous_kid_without_previous_secret` pins that a KID alone does not bind).

**How to apply:** never add a "rotate the mask" flag; a re-key is an owner data migration. Any new key that protects persisted data is presence-only with a pre-stop `--check`. A keep-on-unset rule must share its "unset" predicate with whatever binds the key. A by-hand tool that touches secrets must prove and print the workspace host before its first call. Prove "no value read" with a recording `get_secret` spy that ANSWERS (a raising fake hides a read that swallows its own error). Related: [[bundle-experiment-name-rewrite]].
